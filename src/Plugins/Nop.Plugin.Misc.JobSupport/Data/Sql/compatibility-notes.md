| Legacy behaviour | Intended behaviour | New behaviour | Validation case |
|---|---|---|---|
| The profile type value was calculated but its filter was not applied. | A supplied profile type restricts the search results. | The plugin search applies `@ProfileType` when it is not null. | Search for each profile type and verify every returned row has the requested type. |
| Profile and relationship result sets were paged inconsistently. | Both procedures use stable, repeatable paging. | Both procedures apply `OFFSET` and `FETCH` after a deterministic ordering that ends with `ProfileId`. | Request adjacent pages containing tied sort values and verify that rows do not overlap or disappear. |
| The total-record output was not assigned consistently. | The filtered count is assigned before paging. | Both procedures assign `@TotalRecords` from the complete filtered result set. | Compare `@TotalRecords` with the number of unpaged matching rows. |
| Role, product, shopping-cart type, and specification identifiers were embedded in procedure logic. | Procedure behaviour is controlled by bound parameters and plugin-owned data. | The plugin procedures use their declared parameters and plugin relationship, skill, and subscription columns. | Change configured identifiers and verify that the bound parameter values determine the results. |
| Many-to-many joins could return the same profile more than once. | Skill filtering does not multiply profile rows. | Skill filters use `EXISTS`, and skill names are aggregated once per profile. | Assign multiple primary and secondary skills to a profile and verify one search row is returned. |
